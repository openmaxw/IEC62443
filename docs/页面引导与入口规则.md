# IEC 62443 协同工作台页面引导与入口规则

## 1. 文档目的

本文档基于当前实现，归纳各主页面已经采用或应保持一致的引导方式，确保用户进入任一页面时都能理解：
- 这页解决什么任务
- 当前应该由谁主导
- 这页与上下游页面如何衔接

## 2. 当前页面引导的统一原则

### 2.1 以任务而不是功能命名
当前系统更适合使用任务语言，而不是组件语言。页面标题、摘要和主按钮应优先回答：
- 现在要完成什么
- 完成后交给谁
- 会生成什么结果

例如：
- “业主输入”优于“风险问卷”
- “集成设计工作台”优于“规划配置页”
- “选型匹配与闭环中心”优于“差距页”

### 2.2 以阶段感组织页面
当前系统已经有明确阶段主线：
- 工作台
- 业主输入
- 集成设计
- 设备声明
- 闭环
- 交付汇总

因此每个主页面顶部都应尽量明确：
- 当前处于第几阶段
- 上一步是什么
- 下一步会流向哪里
- 当前输出是否已经可交接

### 2.3 主按钮只服务当前情境
结合当前实现，CTA 应根据阶段状态动态变化：
- 首次进入：显示“开始当前任务”
- 有草稿未完成：显示“继续当前任务”
- 阶段已完成：显示“查看当前结果”
- 当前缺少前置条件：显示补齐前置输入，而不是跳到不适合的后续页

### 2.4 页面摘要要体现交接关系
本系统不是单人单页工具，因此每页摘要文案都应强调：
- 本页输入会被谁使用
- 本页结果会流向哪里
- 本页是否为正式交接节点

## 3. 当前页面的推荐引导定位

### 3.1 Landing
页面作用：解释系统定位、角色关系与工作流主线。

建议保持：
- 强调这是“协同分析与交付辅助系统”
- 强调不是认证或合规判定工具
- 提供进入 Dashboard 或直接进入当前阶段的入口

### 3.2 Dashboard
页面作用：统一查看项目状态、缺失输入与下一步建议。

当前已具备的引导价值：
- 根据 `useProjectStatus()` 显示整体完成度
- 显示缺失输入
- 显示推荐下一步
- 显示各阶段卡片与子步骤

因此 Dashboard 的主文案应持续围绕：
- 当前项目到了哪里
- 为什么建议先做这一步
- 哪些结果已经可以查看或交接

### 3.3 Owner / Owner Result
页面作用：把业务语言整理成可供设计引用的结构化输入。

引导重点：
- 说明适用角色是业主侧、项目负责人、需求提出方
- 强调填写重点是业务后果、暴露面、边界与关键对象
- 明确结果页将被集成商作为设计输入使用

Owner Result 应持续被定义为：
- 正式交接页
- 风险关注与控制目标摘要页
- 业主到集成商的输入桥梁

### 3.4 Integrator / Integrator Result
页面作用：把风险输入翻译成系统设计语言。

引导重点：
- 说明适用角色是集成商、方案设计方、设计负责人
- 强调不是单纯画网络，而是沉淀设计依据、Zone / Conduit、通信约束和能力需求
- 强调结果页会成为设备声明和匹配分析的直接输入

Integrator Result 应持续被定义为：
- 设计输出页
- 要求分配页
- 设备对照的前置页

### 3.5 Vendor / Vendor Result
页面作用：围绕项目要求做能力声明，而不是维护泛化产品档案。

引导重点：
- 说明适用角色是设备商、产品经理、技术支持人员
- 强调需要填写满足方式、证据、依赖和限制
- 强调结果不仅用于展示，还会进入匹配与差距分析

Vendor Result 应持续被定义为：
- 项目化能力摘要页
- 设备声明交接页

### 3.6 Selection
页面作用：汇总设计要求与能力声明，识别差距并形成闭环。

引导重点：
- 说明本页适合项目三方共同查看
- 强调这是“差距识别 + 补偿措施 + 验收影响 + 残余风险”的闭环页
- 对缺口状态做清晰分层：原生满足、配置满足、外部补偿、补偿措施、缺失

### 3.7 Translation Center
页面作用：查看追溯链，而不是单独新增输入。

引导重点：
- 说明它是系统解释中心
- 强调用途是帮助项目成员理解“为什么得到这些要求与差距”
- 明确该页面服务于复核、交接与汇报

### 3.8 Report Center
页面作用：汇总阶段输出与交付准备状态。

引导重点：
- 强调它是交付汇总中心
- 明确哪些交付项已具备、哪些待补齐
- 明确闭环状态、高严重度项和外部依赖项

## 4. 当前导航与入口策略

### 4.1 主导航应围绕流程主线
当前系统最清晰的主链路是：
- `Dashboard`
- `Owner`
- `Integrator`
- `Vendor`
- `Selection`
- `Report`

因此导航和卡片入口都应服务于这条主线，避免把辅助中心与主流程同等并列造成认知分散。

### 4.2 辅助中心应作为补充入口
以下页面更适合被视为辅助中心：
- `Translation Center`
- `Learning`

它们应作为补充查看入口，而不是替代主流程的起点。

### 4.3 兼容路由应减少认知负担
`/gap` 当前已自动重定向至 `/selection`，这类兼容路由应继续弱化，避免用户误解为存在两套不同的差距流程。

## 5. 文案与交互建议

### 5.1 顶部摘要模板建议
每个主页面顶部摘要可尽量包含以下信息：
- 页面目的
- 当前适用角色
- 当前输出对象
- 下一步去向

### 5.2 空状态建议
当阶段数据缺失时，应优先提示：
- 缺少什么输入
- 为什么缺失会阻断当前阶段
- 最短返回路径是什么

避免只显示“暂无数据”这类无指导性的空状态。

### 5.3 结果页建议
所有结果页都应明确三个元素：
- 本页结果基于哪些输入生成
- 本页结果将被谁使用
- 本页仍有哪些待确认项或限制条件

## 6. 对现有系统的结论

结合当前代码实现，可以确认：
- 系统已经具备比较清晰的阶段式 UX 骨架
- Dashboard 已成为流程控制中心
- 各结果页已具备交接节点属性
- Selection、Translation Center、Report Center 已分别承担闭环、追溯、交付三类辅助职能

后续页面优化应以“增强解释、减少跳转歧义、突出交接关系”为主，而不需要重新定义整条主流程。
