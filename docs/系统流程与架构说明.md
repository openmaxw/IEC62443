# 基于现有实现的 IEC 62443 协同工作流与系统架构说明

## 1. 文档目的

本文档用于基于当前代码实现，说明系统已经形成的业务主线、页面协同关系、状态架构与核心引擎职责。

重点不是再讨论“理论上应该怎么做”，而是明确：
- 当前系统已经具备什么
- 各页面如何串联
- 架构上如何支撑从业主输入到交付闭环
- 后续优化应建立在哪些现有能力之上

## 2. 当前系统定位

当前系统已经可以被定义为：

- IEC 62443 驱动的协同分析与交付辅助前端原型
- 围绕单一项目状态对象运行的多角色协同工作流
- 以“风险翻译 -> 设计规划 -> 能力声明 -> 差距闭环 -> 交付汇总”为主线的结构化工具

它不是：
- 自动认证工具
- 合规结论生成器
- 输入极少信息后直接产出唯一正确设计的黑盒系统

## 3. 当前工作流总览

### 3.1 主流程

```text
Landing / Dashboard
  -> Owner Interview / Owner Result
  -> Integrator Workspace / Integrator Result
  -> Vendor Capability / Vendor Result
  -> Selection
  -> Translation Center
  -> Report Center
```

### 3.2 阶段目标

#### 阶段 0：项目建立 / 工作台
目标：建立项目共同上下文，并根据现有数据判断下一步。

当前实现：
- 读取项目元数据
- 计算阶段完成度与子步骤
- 识别缺失输入
- 给出推荐下一步
- 支持重置项目与加载演示项目

#### 阶段 1：业主输入与风险翻译
目标：将业务语言转为结构化风险关注与控制目标。

当前实现：
- 采集项目背景、后果、暴露面、成熟度、关键对象与边界说明
- 输出风险关注、FR 重点、控制目标、集成输入与验收关注点
- 生成可交接的业主结果页

#### 阶段 2：集成设计与要求分配
目标：将业主输入翻译为系统设计语言。

当前实现：
- 记录设计依据
- 维护 zones、conduits、assets、communication flows
- 生成系统规则建议
- 生成能力需求与风险保留项
- 输出可供后续匹配使用的设计结果

#### 阶段 3：设备能力声明
目标：围绕项目要求声明产品满足方式、证据与边界。

当前实现：
- 录入产品元信息
- 录入能力声明项
- 记录安全等级、满足方式、证据、依赖和限制
- 输出设备能力结果页

#### 阶段 4：选型匹配与差距闭环
目标：把系统需求与设备能力对齐，并形成差距闭环记录。

当前实现：
- 计算匹配得分与状态分布
- 识别原生满足、配置满足、外部补偿、补偿措施与缺失项
- 保存 gap closure 条目
- 在交付中心汇总闭环状态

#### 阶段 5：追溯与交付汇总
目标：查看完整追溯链并整理交付准备状态。

当前实现：
- Translation Center 展示业务输入、设计要求、能力与差距的追溯关系
- Report Center 汇总关键交付项与闭环状态
- 支持本地 JSON 导出

## 4. 页面结构与职责

### 4.1 路由现状

当前 `src/App.jsx` 中已明确注册以下主要路由：
- `/`
- `/owner`
- `/owner/result`
- `/integrator`
- `/integrator/result`
- `/vendor`
- `/vendor/result`
- `/selection`
- `/gap`
- `/dashboard`
- `/translation-center`
- `/report`
- `/learning`

这说明系统已经从早期“概念页集合”演化为“具有显式阶段链路的流程型原型”。

### 4.2 页面间关系

#### Landing
负责系统定位、入口引导和流程认知。

#### Dashboard
负责从项目角度统一查看：
- 当前处于哪个阶段
- 缺什么输入
- 下一步去哪
- 各阶段是否已可交接

#### Owner / Owner Result
构成“输入页 + 交接页”组合，保证业主信息不止停留在表单，而能被后续角色消费。

#### Integrator / Integrator Result
构成“设计工作台 + 设计输出页”组合，承接 Owner 结果并生成系统规划和能力需求。

#### Vendor / Vendor Result
构成“声明页 + 结果页”组合，让设备能力对照项目需求，而不是脱离项目独立存在。

#### Selection
承担匹配与闭环主任务，是从设计要求进入设备筛选与差距处理的核心页面。

#### Translation Center
承担追溯视角，用于解释业务输入如何一路变成设计要求、能力项与差距项。

#### Report Center
承担交付汇总视角，用于确认哪些结果已经可交付，哪些闭环仍需补齐。

## 5. 状态管理架构

### 5.1 单一项目状态对象

当前系统以 `ProjectProvider` 为中心，状态已统一收敛为单一项目对象。主要字段包括：
- `projectMeta`
- `ownerProfile`
- `riskTranslation`
- `integratorDesign`
- `vendorCatalog`
- `selectionAnalysis`
- `gapClosure`
- `deliverables`

这意味着系统不是多个孤立页面各自持有状态，而是共享一个可以跨阶段传播的数据骨架。

### 5.2 状态归一化与兼容

`ProjectContext.jsx` 已经实现：
- 默认结构填充
- 旧字段兼容映射
- 数组 / 对象安全归一化
- localStorage / sessionStorage 双写持久化

这保证了当前原型具备比较稳定的：
- 页面刷新恢复能力
- 老数据兼容能力
- 演示项目注入能力

### 5.3 阶段计算与推荐逻辑

`src/hooks/useProject.js` 当前已经提供：
- 阶段定义 `STAGES`
- owner / integrator / vendor / selection 子步骤定义
- 缺失输入计算
- 下一步推荐逻辑
- 各路径聚合读取 hooks

因此，Dashboard、Report Center 等页面已经建立在统一状态判断之上，而不是各写一套判断逻辑。

## 6. 核心引擎架构

### 6.1 风险翻译引擎

`src/utils/riskEngine.js` 负责把业主输入转为结构化风险结果，核心输出包括：
- 风险驱动因子
- 风险关注点
- FR 重点
- 目标等级候选
- 控制目标
- 业主需求
- 验收关注点
- 解释链

这一步实现了从业务后果与暴露面到安全目标语言的第一轮翻译。

### 6.2 设计规划引擎

`src/utils/planningEngine.js` 负责把风险关注与设计输入转为系统规划输出，当前职责包括：
- 生成区域 / 通道相关建议
- 生成边界控制与系统规则建议
- 生成能力需求矩阵
- 输出风险保留项

这一步实现了从风险语言到系统设计语言的第二轮翻译。

### 6.3 匹配分析引擎

`src/utils/matchEngine.js` 负责把能力声明与需求矩阵对齐，输出：
- 明细级状态分类
- 状态分布统计
- 综合得分
- 推荐等级
- 结果排序

当前状态分类至少包括：
- `native`
- `configured`
- `external`
- `compensating`
- `missing`

这一步实现了从系统设计语言到设备能力语言的第三轮翻译。

## 7. 当前系统已经形成的闭环能力

相较于早期“页面还未打通”的阶段，当前实现实际上已经具备以下闭环：

### 7.1 项目闭环
同一项目的元数据、输入和结果在多个页面中共享。

### 7.2 角色闭环
业主输入不再停留在本页面，而会影响集成设计与设备匹配。

### 7.3 结果闭环
匹配结果中的差距项会进一步进入 gap closure 与交付汇总。

### 7.4 解释闭环
Translation Center 和 Report Center 已经承担解释与追溯职责，而非只有单页结果展示。

## 8. 当前实现与文档认知的对齐结论

结合代码现状，以下几点需要作为后续文档的统一认知：
- 当前系统已经具备工作流骨架，不应再把它描述为“零散的页面原型”
- `Dashboard` 已经是流程控制台，不应再描述为简单跳板页
- `owner/result`、`integrator/result`、`vendor/result` 已经是正式交接节点
- `Selection` 已承担差距闭环核心职能，`/gap` 当前只是兼容跳转
- `Translation Center` 与 `Report Center` 已成为系统级辅助中心

## 9. 建议的后续优化方向

后续优化应建立在现有结构之上，而不是推翻重来。优先方向包括：
- 继续增强 Translation Center 的解释复用
- 细化 Report Center 的交付对象与导出能力
- 继续丰富 Vendor 声明中的边界、依赖和证据结构
- 强化 Selection 页中的闭环编辑体验和责任归属表达
- 让 Integrator 设计依据与要求分配解释更完整

## 10. 结论

当前系统已经形成一个以单一项目状态为核心、以三类规则引擎为驱动、以多阶段结果页为交接节点的 IEC 62443 协同前端原型。

后续文档与沟通应默认承认这一点：系统重点已经从“页面搭建”转向“流程深化、解释增强和交付补强”。
