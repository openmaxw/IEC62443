# IEC 62443 工作流稳定性检查清单

## 1. 文档目的

本文档用于约束当前前端原型在继续迭代时的稳定性底线，重点覆盖：
- 项目状态兼容
- 草稿同步稳定性
- 结果页前置条件保护
- 工作台与中心页联动
- 主流程回归路径

## 2. 状态结构与兼容性

### 2.1 新增字段时必须同步更新
凡是给项目状态新增字段，必须同步检查 `src/context/ProjectContext.jsx` 中的：
- 默认值定义
- normalize 函数
- 旧字段兼容映射
- `initialState` 结构
- 存储加载与保存路径

### 2.2 数组与对象必须兜底
- 所有数组字段都应通过 `ensureArray` 兜底
- 所有对象字段都应通过 `ensureObject` 兜底
- 页面读取嵌套对象前，必须假设其可能为空

### 2.3 旧缓存必须可安全加载
当前系统显式依赖 `localStorage` 和 `sessionStorage`，因此每次状态结构变化后都要确认：
- 旧缓存不会导致白屏
- 缺失字段会被自动补齐
- hooks 仍能兼容旧字段与新字段读取路径

## 3. 草稿同步与状态更新

### 3.1 禁止高风险同步模式
- 禁止在 `setState((prev) => ...)` 的 updater 中调用 Context action
- 禁止在 render 期间触发状态写入
- 禁止把明显不稳定的对象引用直接放进 effect 依赖中造成循环同步

### 3.2 推荐同步模式
表单页草稿应尽量保持以下模式：
- 本地 state 负责即时编辑
- `useEffect` 负责把稳定草稿同步到 Context
- Context 再统一写入存储

### 3.3 必查错误类型
每次改动表单同步逻辑后，至少要防止：
- `maximum update depth exceeded`
- render-phase update
- 刷新后草稿丢失
- 新旧数据覆盖顺序异常

## 4. 页面前置条件与空态保护

### 4.1 结果页必须允许前置缺失
以下页面在缺失前置数据时，不应直接崩溃：
- `/owner/result`
- `/integrator/result`
- `/vendor/result`
- `/selection`
- `/translation-center`
- `/report`

### 4.2 列表与对象渲染必须安全
- 所有 `.map()`、`.filter()`、`.length` 访问前都要确保类型安全
- 对象数组展示时，禁止直接渲染对象本身
- `join()` 前要确认元素是可展示文本
- 所有统计值都要允许空数组和空对象输入

### 4.3 重定向与兼容入口要稳定
- `/gap` 必须稳定重定向到 `/selection`
- `redirect` 查询参数处理不能造成异常历史状态
- 路由 basename 处理不能破坏直接访问和刷新

## 5. 工作台与中心页联动检查

### 5.1 Dashboard
每次改动阶段逻辑后，必须检查：
- `useProjectStatus()` 是否仍可正确计算完成度
- 缺失输入提示是否与真实数据一致
- 下一步推荐是否仍然合理
- 子步骤状态是否与当前页面结构一致

### 5.2 Translation Center
每次改动风险翻译、规划结果或匹配结果后，必须检查：
- 追溯链仍然可展示
- 缺失中间数据时不会崩溃
- 文案解释与当前引擎输出结构一致

### 5.3 Report Center
每次改动匹配与闭环逻辑后，必须检查：
- 交付项状态是否准确
- gap closure 数量统计是否准确
- 高严重度与外部依赖数量是否准确
- 在无闭环项时空态是否仍正常

## 6. 核心引擎稳定性检查

### 6.1 风险翻译引擎
涉及 `src/utils/riskEngine.js` 的改动后，至少检查：
- `drivers`、`riskConcerns`、`frFocus` 等结构是否稳定
- 业主结果页与追溯页是否仍可读取
- 新增规则不会破坏已有演示项目输出

### 6.2 规划建议引擎
涉及 `src/utils/planningEngine.js` 或 `src/utils/designInputEngine.js` 的改动后，至少检查：
- `zones`、`conduits`、`communicationFlows`、`capabilityRequirements` 是否仍可生成
- 集成结果页与 Selection 是否仍可读取
- 风险保留项与规则建议是否仍安全渲染

### 6.3 匹配分析引擎
涉及 `src/utils/matchEngine.js` 的改动后，至少检查：
- 五类状态分类是否仍完整
- 综合得分与推荐等级是否可生成
- Selection、Report Center 是否仍可读取结果

## 7. 主流程回归路径

### 7.1 空白项目路径
至少验证：
- `Dashboard -> Owner -> Integrator -> Vendor -> Selection -> Report`

### 7.2 演示项目路径
至少验证：
- 加载演示项目后逐页打开所有主流程页面
- Translation Center 和 Report Center 能正常读取结果

### 7.3 刷新恢复路径
至少验证：
- Owner / Integrator / Vendor 填写中途刷新页面，草稿仍可恢复

### 7.4 旧缓存兼容路径
至少验证：
- 旧 `localStorage` / `sessionStorage` 存在时，系统仍可启动并显示空态或默认值

## 8. 视觉与结果页一致性

### 8.1 结果页风格应延续现有稳定模式
新增结果页或大幅改造结果页时，应尽量对齐现有稳定页面的：
- 卡片边框与圆角变量
- 深色半透明面板风格
- 状态标签与摘要区结构
- 空态与提示块表现

### 8.2 避免信息层级倒置
- 先显示结论、状态、下一步
- 再显示解释、背景、补充说明
- 避免长段说明压过关键状态信息

## 9. 提交前快速自检

每次提交前至少快速检查以下几点：
- 是否新增了项目状态字段但漏改 normalize / default
- 是否引入了对象直接渲染风险
- 是否引入了不安全的 `.map/.filter/.length` 访问
- 是否让结果页在缺失前置数据时崩溃
- 是否破坏了 Dashboard 的阶段判断与下一步推荐
- 是否破坏了 `/gap` 到 `/selection` 的兼容跳转
- 是否破坏了刷新恢复和演示项目加载

## 10. 结论

当前系统的稳定性重点不在“复杂算法正确性”，而在“状态结构兼容、主流程不断、结果页不崩、追溯与交付中心可持续读取”。

后续迭代应始终以这四点作为最低稳定性底线。
