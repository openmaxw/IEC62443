# 系统干净标准与契约基线

## 1. 这份文档解决什么问题

这份文档不是为了描述“页面看起来是否统一”，而是为了定义：

- 这个系统从底层到高层，什么才叫“干净”；
- 当前项目中，哪些点已经具备雏形；
- 哪些地方仍然是导致反复出错的根因；
- 后续整改时，应该优先统一哪些契约，而不是继续点状补 bug。

一句话定义：

> 干净的系统，不是没有缺陷，而是数据形状可预测、状态边界明确、组件契约单一、交互退化一致、错误可被局部吸收。

---

## 2. 当前项目的核心对象

结合 `src/context/ProjectContext.jsx` 当前状态结构，系统核心对象已经比较清晰：

- `projectMeta`：项目元信息
- `ownerProfile`：业主输入，分为 `assessment` 与 `draft`
- `riskTranslation`：风险翻译结果，核心为 `profile`
- `integratorDesign`：集成设计，分为 `plan` 与 `draft`
- `vendorCatalog`：厂商能力声明，包含 `capabilities` 与 `draft`
- `selectionAnalysis`：能力匹配与选型结果，核心为 `results`
- `gapClosure`：闭环措施集合，核心为 `items`
- `deliverables`：交付物，核心为 `reports`

这说明系统已经有了“阶段化对象”的骨架，这是好事。

但问题在于：**对象存在，不等于对象契约稳定。**

---

## 3. 干净系统的五层标准

### 3.1 数据模型层干净

标准：

- 每个核心对象都必须有稳定 schema；
- 每个字段都要明确是：必填 / 可选 / 可空；
- 数组字段必须约定默认值为 `[]`；
- 对象字段必须约定默认值为 `null` 或标准空对象；
- 同一语义只能有一套正式字段，不应长期并存历史兼容字段。

当前项目的现实情况：

- 顶层对象已经被 `normalizeState()` 统一过一轮；
- 但对象内部字段没有做完整 schema 化；
- 例如 `integratorDesign.plan` 存在时，其内部的 `zones`、`assets`、`communicationFlows`、`capabilityRequirements` 不保证始终为数组；
- 因此页面层仍在反复承担“字段可能缺失”的风险。

结论：

- **顶层状态已有归一化；内部业务对象尚未完成归一化。**

### 3.2 状态流转层干净

标准：

- 每个阶段只产出一种标准结果；
- 草稿态与结果态边界清楚；
- 下游页面消费的是上游的“标准输出”，而不是半成品；
- 任一阶段未完成时，系统应该进入已定义的空态或待完成态，而不是异常态。

当前项目的真实流转可概括为：

- `projectMeta`
- `ownerProfile.assessment`
- `riskTranslation.profile`
- `integratorDesign.draft / plan`
- `vendorCatalog.draft / capabilities`
- `selectionAnalysis.results`
- `gapClosure.items`
- `deliverables.reports`

问题在于：

- 有些页面消费 `draft`；
- 有些页面消费 `plan`；
- 有些逻辑同时从新结构和 legacy 字段回退读取；
- `createLegacyCompatState()` 还在持续输出兼容字段，这会让“当前正式契约”长期模糊。

结论：

- **状态流顺序是对的，但阶段边界还不够硬。**

### 3.3 页面与组件契约层干净

标准：

- 页面不要直接深挖原始全局状态；
- 页面应只消费 selector / view model 输出；
- 页面内部不应该到处写 `?.`、`|| []`、`|| ''`；
- 组件不应自行猜测数据形状，输入契约必须单一。

当前项目的现实情况：

- 已有 `useOwnerPath()`、`useIntegratorPath()`、`useVendorPath()` 这样的路径型 hooks；
- 这是好方向；
- 但这些 hooks 目前只保证顶层对象存在，不保证对象内部字段形状稳定；
- 因此结果页、工作台页、摘要页仍有大量直接 `.length`、`.map`、`.filter` 访问。

结论：

- **已经有 selector 的雏形，但还没有形成真正的 ViewModel 层。**

### 3.4 交互行为层干净

标准：

- 同类页面在空态、未完成态、完成态、返工态下行为一致；
- 页面遇到缺数据时应该呈现明确提示，不应直接崩；
- 从编辑页进入结果页、再返回编辑页，回填与保存逻辑应一致。

当前项目的现实情况：

- 一部分结果页空态已经比较友好；
- 但仍存在“部分缺字段时不显示空态，而是直接访问数组字段”的情况；
- 这说明页面更像是在假设“数据已完整”，而不是显式处理“数据可能不完整”。

结论：

- **交互视觉风格在统一，交互状态机还没有完全统一。**

### 3.5 错误与防线层干净

标准：

- 写入时校验；
- 读取时归一化；
- 页面渲染前做 view model 收口；
- 页面异常只作为最后一道防线，而不是第一道防线。

当前项目的现实情况：

- 现在很多问题是靠页面局部补兜底发现的；
- 说明“归一化发生得太晚”；
- 一旦页面自己忘了兜底，就会直接炸在 render。

结论：

- **当前系统具备局部兜底能力，但缺少统一防线。**

## 4. 当前项目为什么会反复出现“统一后仍出错”

根因不是“你做得不够仔细”，而是下面四件事还没有同时成立：

- 数据对象名统一了，但内部字段默认值没统一；
- 页面结构统一了，但消费数据的方式没统一；
- 路由流程统一了，但阶段结果和草稿的边界没统一；
- 组件样式统一了，但缺省态和异常态处理没统一。

所以你会感受到一种典型现象：

- 页面看着很整齐；
- 代码目录也开始统一；
- 但真实点一点仍会暴露裂缝。

这正是“外层统一先行、系统契约滞后”的表现。

---

## 5. 这个项目里，什么才算真正的“干净”

如果把“干净”变成可以落地检查的标准，可以用下面十条：

1. 所有核心对象都有标准 schema。
2. 所有数组字段都有统一默认值 `[]`。
3. 所有结果页只消费标准结果对象，不直接吃草稿态半成品。
4. 所有页面只通过 selector / view model 取数。
5. 同类页面的空态、未完成态、完成态行为一致。
6. 所有 `.map/.filter/.length` 前都不依赖页面作者手写兜底。
7. legacy 兼容字段只存在于兼容层，不扩散到业务页面。
8. 状态写入动作只产出一种正式数据形状。
9. 改一个字段时，影响页面范围可预测。
10. 错误边界只拦真正异常，不拦“正常缺数据”。

只要这十条里还有几条没做到，系统就很难给人“没有瑕疵”的感觉。

## 6. 当前项目建议采用的正式架构准则

### 6.1 一切页面都不直接吃原始状态

页面只允许吃两类东西：

- 标准 domain object
- 标准 view model

禁止页面直接在 JSX 里处理：

- 历史兼容字段回退
- 旧字段名兼容
- 数组缺省补齐
- 文本空值归一化

这些都应该在 selector / normalizer 层完成。

### 6.2 每个阶段必须同时定义 Draft 和 Result

建议明确：

- `ownerProfile.draft`
- `ownerProfile.assessment`
- `riskTranslation.profile`
- `integratorDesign.draft`
- `integratorDesign.plan`
- `vendorCatalog.draft`
- `vendorCatalog.capabilities`
- `selectionAnalysis.results`
- `gapClosure.items`
- `deliverables.reports`

其中：

- 编辑页原则上读 `draft`
- 结果页原则上读 `assessment / profile / plan / results / reports`
- 不允许结果页直接依赖“可能未整理完成的 draft 内部细节”

### 6.3 每个核心对象都需要对象级 normalize

例如不应只写：

- `integratorDesign.plan || null`

而应写成类似：

- `normalizeIntegratorPlan(plan)`

它至少应统一：

- `zones`
- `conduits`
- `assets`
- `communicationFlows`
- `capabilityRequirements`
- `designBasisSummary`

同理还应该有：

- `normalizeOwnerAssessment()`
- `normalizeRiskProfile()`
- `normalizeVendorCapabilityDraft()`
- `normalizeMatchResults()`
- `normalizeGapClosureItems()`

### 6.4 页面只拿“能直接渲染”的 ViewModel

例如结果页不直接拿 `plan`，而拿：

- `integratorResultViewModel`

它应当已经包含：

- 统计数字
- 已格式化 chips
- 空态文案
- 已归一化表格数据
- 是否 ready / empty / invalid

这样结果页就是“纯展示层”，更难出错。

## 7. 当前代码中的主要结构性风险

基于现状，主要风险不是单点 bug，而是以下结构性风险：

### 风险 1：顶层归一化到位，内层归一化不足

表现：

- `plan` 不为 `null`，但 `plan.assets` 可能为 `undefined`
- `results` 不为 `null`，但内部 `rows`、`summary`、`stats` 不一定完整

后果：

- 页面作者很容易误判“对象存在 = 对象完整”

### 风险 2：legacy 兼容字段仍在业务流中扩散

表现：

- `normalizeState()` 与 `createLegacyCompatState()` 同时维护新旧结构
- hooks 与页面里仍有 `a ?? b ?? c` 式回退

后果：

- 正式契约无法收敛
- 页面作者不知道该依赖哪一套字段才算“正确”

### 风险 3：页面承担了过多数据清洗责任

表现：

- 页面里直接做数组兜底、字段回退、空值兼容

后果：

- 同一类问题会在不同页面重复出现
- 修复成本随页面数线性增加

### 风险 4：状态阶段存在“名义分层，实际混用”

表现：

- `draft` 与 `plan` 在部分流转中边界不够硬
- 保存动作常常同时覆盖多个层次

后果：

- 页面看似消费结果，实际拿到的是草稿形状

## 8. 后续整改优先级

建议严格按下面顺序推进，而不是继续随机修页面。

### P0：定义核心 schema

先产出一份项目正式 schema，至少覆盖：

- `ProjectMeta`
- `OwnerAssessment`
- `RiskProfile`
- `IntegratorPlan`
- `VendorCapabilityDraft / CapabilityRecord`
- `SelectionResults`
- `GapClosureItem`
- `DeliverableReport`

目标：让每个对象字段的“类型、默认值、可空规则”固定下来。

### P1：建立对象级 normalize 层

在 `src/context` 或 `src/domain` 下建立统一 normalizer：

- `normalizeOwnerAssessment`
- `normalizeRiskProfile`
- `normalizeIntegratorPlan`
- `normalizeSelectionResults`
- `normalizeGapClosureItems`

目标：以后页面不再各自补 `|| []`。

### P2：建立 selector / view model 层

例如：

- `getOwnerResultViewModel(state)`
- `getIntegratorResultViewModel(state)`
- `getSelectionResultViewModel(state)`

目标：页面改为只消费可直接渲染的数据。

### P3：统一页面状态机

给所有主页面统一状态：

- `empty`
- `draft`
- `ready`
- `invalid`
- `completed`

目标：让空态、缺失态、回退态在所有页面上行为一致。

### P4：收缩 legacy 兼容层

目标：

- 兼容逻辑只保留在加载与迁移层；
- 页面层、hooks 层、业务层不再直接依赖旧字段。

---

## 9. 这份基线文档对应的工程判断

从工程视角看，这个项目**不是烂系统**，而是一个：

- 业务流已经成型；
- 页面层统一已开始；
- 但系统契约层还未完全收口的系统。

所以后续目标不应是：

- “再也不允许出现 bug”

而应是：

- “同类 bug 以后只能在一层出现一次，修一次即可全局收口”。

这才是“干净系统”的真正标志。

---

## 10. 下一步建议

如果按最稳妥的方式推进，建议后续分两步：

1. 先把正式 schema 文档补出来；
2. 再开始把 `useOwnerPath / useIntegratorPath / useVendorPath` 升级为真正的 selector + view model 层。

也就是说，下一轮不要先修页面，而是先修“页面为什么会拿到脏数据”的根。

## 11. 建议的最小落地动作

为了把这份基线尽快转成工程收益，建议先做下面三个最小动作：

- 动作 1：补 `IntegratorPlan`、`OwnerAssessment`、`SelectionResults` 的正式 schema 文档；
- 动作 2：在 `src/context` 或 `src/domain` 建对象级 normalizer；
- 动作 3：先把结果页全面切到 view model，停止页面内直接兜底。

推荐优先顺序：

- 第一周：schema + normalizer
- 第二周：selector / view model
- 第三周：结果页与摘要页切换
