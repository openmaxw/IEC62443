# 稳定性治理与副作用排查规则

## 1. 目的

本文档用于约束后续功能开发和重构过程中，对 `useEffect`、本地状态、Context 状态和持久化同步进行统一排查，避免出现死循环、重复渲染和状态回写抖动。

---

## 2. 当前已发现的典型风险模式

### 2.1 本地状态与 Context 草稿双向同步
典型表现：
- 页面有本地 `useState`
- `useEffect` 每次把本地状态写回 Context
- Context 更新后又通过 `useEffect` 回写本地状态
- 形成更新回路

高风险页面类型：
- 需求输入页
- 设计输入页
- 能力声明页
- 闭环编辑页

### 2.2 对象 / 数组依赖导致 effect 反复触发
典型表现：
- effect 依赖项中包含 render 时变化的新对象 / 新数组
- 内容未变，但引用每次变化
- effect 不断触发

### 2.3 Reducer 无差异更新
典型表现：
- dispatch 相同内容
- reducer 仍返回新对象
- 导致 Context value 改变
- 下游 effect 再次触发

---

## 3. 统一排查规则

### 3.1 所有 `useEffect` 都必须回答四个问题
1. 这个 effect 是否会触发 `setState` 或 `dispatch`
2. 它依赖的值是否可能在每次 render 都变
3. 它是否会被自己的更新结果再次触发
4. 是否有“不同才更新”的保护

### 3.2 凡是把本地状态写回 Context，必须加比较保护
禁止：
- `useEffect(() => actions.setX(localState), [localState])`

允许：
- 只有在新旧值不同的情况下才 `dispatch`

### 3.3 凡是把 Context 数据回灌本地状态，必须加比较保护
禁止：
- `useEffect(() => setLocal(globalDraft), [globalDraft])`

允许：
- 只有在新旧值不同的情况下才 `setState`

### 3.4 Reducer 层也必须兜底
即使页面层做了保护，Reducer 仍应对关键 draft / result 更新做无差异返回。

目标：
- 相同 payload 不触发新 state
- 相同 state 不触发新的 Context value 变化

---

## 4. 当前建议的治理顺序

1. 先扫描所有 `useEffect`
2. 标记所有会 `setState` / `dispatch` 的 effect
3. 检查其依赖项是否包含对象 / 数组
4. 为页面层同步加比较保护
5. 为 reducer 层关键 action 加无差异返回
6. 再做构建与交互验证

---

## 5. 后续开发默认要求

后续新增页面或新增编辑态时，必须遵守：
- 本地编辑态与 Context 草稿态不能无条件双向同步
- effect 内部所有回写都要做差异判断
- reducer 对关键同步 action 做去重保护
- 能单向同步的地方不要设计成双向同步

---

## 6. 当前结论

当前系统已经进入统一 UI 体系，但稳定性治理必须单独作为一条工作线执行。
后续所有功能修改，除 UI 和业务检查外，还必须经过“副作用与同步链路检查”。
