# 统一设计优化评估与优化计划

> 本文档用于评估“业主、FAE、销售、集成商、设备商、产品经理、公司高管”等多角色优化是否会影响当前系统统一设计，并给出后续可落地的产品与工程路线图。
>
> 核心结论：这些优化不会破坏统一设计，前提是所有新增能力都服务于同一条项目链路：**项目输入 → 风险转译 → 设计响应 → 能力声明 → 匹配闭环 → 追溯 / 交付摘要**。

## 1. 总体判断

当前系统已经具备较清晰的统一底座：

- **统一项目对象**：所有页面围绕同一个项目状态推进，而不是每个角色各自维护一套数据。
- **统一流程主线**：需求澄清、风险转译、设计响应、能力声明、匹配闭环、追溯和交付摘要构成连续链路。
- **统一页面骨架**：核心业务页已经采用阶段页壳、状态摘要、步骤页签、说明区和统一按钮风格。
- **统一交付口径**：报告与页面说明反复强调非认证结论、非合规结论、非正式工程设计依据。
- **统一专业语言**：IEC 62443 的 FR / SR / SL、Zone / Conduit、能力声明和差距闭环已经形成基础表达体系。

因此，多角色优化本身不是风险。真正的风险在于：如果每个角色都新增一套独立入口、独立输出、独立口径，系统会从“统一项目协同工作台”退化成“多个角色页面拼盘”。

后续优化应坚持：**一个项目对象，多角色视角；业务语言输入，标准语言沉淀；所有输出都能追溯回原始输入。**

## 2. 统一设计可能被破坏的风险

### 2.1 角色入口过多导致系统割裂

如果分别为业主、销售、FAE、集成商、设备商、PM、高管建立独立流程，用户会难以理解哪个入口才是主流程，项目数据也会变得重复和不一致。

**应对原则**：

- 不新增孤立的“销售流程”或“高管流程”。
- 销售、FAE、管理层视图都应是现有项目链路的不同视角。
- 新入口只能用于快速启动或查看摘要，不能绕过主链路。

### 2.2 销售化表达削弱专业可信度

销售需要快速讲价值，但如果系统过度营销化，会削弱 IEC 62443 项目前期协同工具的可信度。

**应对原则**：

- 销售摘要必须来自项目输入、风险关注、设计响应、能力声明和差距状态。
- 不生成脱离项目事实的宣传话术。
- 保留免责声明，明确不构成认证、合规或正式工程设计结论。

### 2.3 设备能力边界被误读

如果能力声明只显示“满足 / 不满足”，设备商可能担心系统把项目责任错误转嫁给产品。

**应对原则**：

- 能力声明必须区分：产品原生满足、配置后满足、需集成共同实现、需外部补偿、当前不满足、不适用。
- 证据、前提条件、外部依赖和限制条件必须与满足度一起呈现。
- 差距闭环需要明确责任方，不默认设备商负责所有缺口。

### 2.4 管理层视图脱离项目事实

高管需要业务价值，但如果管理层视图只展示抽象价值口号，会和系统的项目协同本质脱节。

**应对原则**：

- 管理层视图应展示来自项目链路的指标，例如差距闭环率、待确认输入数、能力满足比例、可复用模板数。
- 不把系统包装成正式认证平台、风险评估平台或完整工程设计平台。
- 管理层看到的是“协同效率和风险前置”的价值，而不是替代专家判断。

## 3. 分角色挑刺与公正评判

### 3.1 业主方

**他们会挑刺**：

- 术语仍然偏专业，例如 IEC 62443、Zone / Conduit、FR / SR / SL、能力声明。
- 他们更关心停机、生产影响、远程维护、第三方责任、验收压力和预算优先级。
- 如果一开始就要求填写太多专业字段，容易放弃。

**合理部分**：

业主入口确实应更业务化。系统应先帮助业主说清楚“担心什么、影响什么、谁接入、怎么验收”，再把这些内容转译成标准语言。

**不应过度迎合**：

不能为了降低门槛而取消标准映射。业主可以不直接面对 IEC 62443 术语，但系统内部和结果页仍要沉淀为可追溯的标准语言。

**优化方向**：

- 输入页优先使用业务语言。
- 结果页再解释对应的 IEC 62443 项目表达。
- 增加“我不知道怎么填”的提示和示例。

### 3.2 集成商

**他们会挑刺**：

- 仅有文字化设计响应还不够支撑真实方案设计。
- 缺少拓扑、区域边界、通信路径、接口清单、责任边界等工程输入。
- 差距闭环需要能形成客户可确认的记录。

**合理部分**：

集成商需要把业主输入转成可执行方案。系统目前更适合前期沟通，还未完全覆盖详细工程设计。

**不应过度迎合**：

系统不应扩展成完整工程设计工具，否则会偏离“项目前期需求转译与对齐”的定位。

**优化方向**：

- 增加责任矩阵和接口边界摘要。
- 增强 Zone / Conduit 与通信路径的结构化描述。
- 输出可用于客户确认的差距与责任记录。

### 3.3 设备商

**他们会挑刺**：

- 项目能力需求可能被误解为产品必须单独满足。
- 证据类型和适用边界不够细，会增加承诺风险。
- 外部依赖、配置条件和补偿措施需要更明确。

**合理部分**：

设备能力不能被简单等同为项目安全能力。很多能力需要产品、系统集成、运维制度和外部控制共同实现。

**不应过度迎合**：

不能让设备商用“外部依赖”模糊所有责任。每条能力仍需说明产品能提供什么、不能提供什么、证据是什么。

**优化方向**：

- 标准化能力满足度分类。
- 标准化证据类型。
- 在能力声明中突出适用范围、前提条件、外部依赖和限制。

### 3.4 销售

**他们会挑刺**：

- 系统专业但不一定知道如何用于推进商机。
- 缺少客户痛点、推荐话术、下一步行动和简短摘要。
- 如果不能快速形成客户可读材料，使用动力会弱。

**合理部分**：

销售需要更快地把系统用于客户沟通，而不是完整走完所有专业页面后才看到价值。

**不应过度迎合**：

不要把系统改造成 CRM，也不要生成脱离事实的销售话术。

**优化方向**：

- 增加一页式客户摘要。
- 增加下一步沟通建议。
- 增加典型场景模板，帮助销售快速启动讨论。

### 3.5 FAE / 售前技术

**他们会挑刺**：

- 客户现场沟通时间有限，需要 15–30 分钟内产出初步结论。
- 需要远程维护、IT/OT 边界、第三方接入、日志审计等典型模板。
- 需要可复用问答脚本和演示项目。

**合理部分**：

FAE 是最可能高频使用该系统的角色。系统应帮助他们快速把客户问题转成结构化输入和方案讨论框架。

**不应过度迎合**：

快速模式不能绕过风险转译、设计响应、能力声明和差距闭环，只能加速启动。

**优化方向**：

- 建立快速场景模板库。
- 建立一页式客户摘要。
- 建立现场沟通问题清单。

### 3.6 产品经理

**他们会挑刺**：

- 系统能收集项目需求，但暂时难以沉淀为产品需求洞察。
- 缺少能力缺口频次、行业关注点、证据需求类型等统计维度。
- 如果只有自由文本，难以支撑 roadmap 判断。

**合理部分**：

系统长期可以成为产品需求洞察来源，但前提是数据结构足够稳定。

**不应过度迎合**：

不能把销售备注直接当作产品需求，也不能用少量项目样本做过度结论。

**优化方向**：

- 导出结构化需求与能力缺口数据。
- 增加行业、场景、能力、证据类型等统计维度。
- 将 PM 洞察定位为输入参考，而不是路线图自动决策。

### 3.7 公司高管

**他们会挑刺**：

- 系统看起来专业，但商业价值需要更直观。
- 需要知道它能缩短售前周期、提升客户信任、减少后期返工，还是支持产品战略。
- 如果没有指标，只会被看作一个演示原型。

**合理部分**：

管理层需要看到业务价值和可复制打法。

**不应过度迎合**：

不能为了高管视图夸大系统能力。它不是认证平台，也不是正式风险评估或工程设计替代品。

**优化方向**：

- 增加管理层价值视图。
- 展示售前效率、风险提前暴露、差距闭环率和模板复用情况。
- 明确系统在业务链条中的位置：前期沟通、需求澄清、方案对齐、能力边界说明。

## 4. 优化路线图

### 4.1 P0：FAE / 销售快速沟通能力

**目标**：让系统可以在客户沟通早期快速产生价值，帮助 FAE / 销售用统一语言开启需求澄清。

**输入**：

- 典型场景选择。
- 客户行业、项目目标、关键系统、外部连接、远程维护、验收关注。

**输出**：

- 预填的项目输入草稿。
- 初步风险关注。
- 一页式客户摘要。
- 下一步待确认问题。

**建议新增能力**：

- 快速场景模板：远程维护、IT/OT 边界、产线分区、第三方接入、日志审计、补丁维护。
- 一页式客户摘要：客户痛点、初步风险关注、建议下一步、待确认问题、免责声明。
- 页脚、README、报告中的授权与免责声明口径一致性检查。

**不做事项**：

- 不新增独立 CRM 流程。
- 不生成脱离项目事实的营销话术。
- 不绕过现有项目链路。

### 4.2 P1：业主入口与能力边界强化

**目标**：降低业主填写门槛，同时降低设备能力被误读的风险。

**输入**：

- 业主业务语言输入。
- 产品能力、证据、配置前提、外部依赖和限制条件。

**输出**：

- 更易理解的业主输入摘要。
- 更清晰的设备能力边界声明。
- 更正式的差距责任矩阵。

**建议新增能力**：

- 业主低门槛问题：停机影响、远程接入、第三方维护、验收压力、责任边界。
- 能力满足度分类：产品原生满足、配置后满足、需集成共同实现、需外部补偿、当前不满足、不适用。
- 证据类型：datasheet、manual、configuration guide、test report、certificate、project evidence、statement。
- 差距责任矩阵：责任方、补偿措施、验收影响、残余风险、关闭条件。

**不做事项**：

- 不把业主输入页变成 IEC 62443 考试。
- 不让设备商默认承担所有项目差距。
- 不替代正式工程设计和现场验证。

### 4.3 P2：PM 洞察与管理层价值视图

**目标**：让项目数据能沉淀为产品和业务决策参考。

**输入**：

- 多项目结构化数据。
- 行业、场景、能力需求、证据需求、差距状态。

**输出**：

- PM 需求洞察导出。
- 管理层价值摘要。
- 可复用模板和常见差距统计。

**建议新增能力**：

- 需求洞察导出：行业、场景、能力缺口、证据类型、目标 SL 分布。
- 管理层视图：售前效率、风险提前暴露、差距闭环率、可复用模板数。
- 模板复用统计：哪些场景被频繁使用，哪些能力经常出现缺口。

**不做事项**：

- 不把少量项目样本直接等同为市场结论。
- 不把主观销售备注直接作为产品需求依据。
- 不在当前阶段引入复杂后端、登录、多用户和权限系统。

## 5. 统一设计护栏

后续每次新增功能，都应先检查是否满足以下护栏：

1. **是否仍围绕同一个项目对象？**
   - 是：可以进入设计。
   - 否：需要重新评估，避免形成孤立系统。

2. **是否仍回到主链路？**
   - 必须能落到项目输入、风险转译、设计响应、能力声明、匹配闭环、追溯或交付摘要中的至少一个环节。

3. **是否有可追溯来源？**
   - 所有摘要、建议和结论都应说明来自哪些输入或状态。

4. **是否保持系统边界？**
   - 不构成认证结论。
   - 不构成合规结论。
   - 不构成正式风险评估。
   - 不替代详细工程设计、专家评审或现场验证。

5. **是否避免责任误导？**
   - 对设备能力、系统集成、业主运维、外部补偿和残余风险进行清晰区分。

6. **是否复用统一组件和 view model？**
   - 页面新增展示应优先复用现有页面壳、状态摘要、表格、卡片、提示区和报告生成机制。

## 6. 后续工程落地建议

### 6.1 模板库驱动快速体验

典型场景模板应作为结构化数据维护，而不是硬编码在页面中。模板至少应包含：

- 场景名称。
- 适用对象。
- 常见客户痛点。
- 建议提问。
- 默认关注的风险方向。
- 可能涉及的能力项。
- 待确认问题。

模板用于预填项目输入草稿和生成初步摘要，但不能直接跳过用户确认。

### 6.2 用 view model 生成多受众摘要

不同受众看到的信息可以不同，但业务逻辑不应复制。

建议将摘要生成集中在 view model 层：

- FAE / 销售摘要：客户痛点、风险关注、下一步问题。
- 业主摘要：业务影响、验收关注、待补输入。
- 集成商摘要：设计依据、边界、接口、能力需求。
- 设备商摘要：能力满足度、证据、依赖和限制。
- 管理层摘要：项目成熟度、差距闭环、业务价值指标。

### 6.3 继续使用统一报告生成机制

交付摘要应继续由统一 report generator 输出，避免出现多套报告逻辑。

一页式客户摘要可以作为报告的一种轻量模式，但仍应使用同一批项目状态和免责声明。

### 6.4 保持公开版边界

当前公开版仍应定位为前端原型和方法演示工具。后续如果要保护核心价值，应考虑：

- 公开仓库只保留演示逻辑和示例数据。
- 核心规则库、模板库和报告策略可迁移到私有仓库或后端服务。
- 对外演示保留版权和使用限制声明。

## 7. 验收检查清单

文档或功能进入下一阶段前，应检查：

- 是否覆盖统一性评估、角色评判、路线图和工程落地建议。
- 是否所有优化建议都回到现有主链路。
- 是否每个 P0 / P1 / P2 项都有明确目标、输入、输出和不做事项。
- 是否保留授权、免责声明、非认证结论、非正式工程设计依据等边界。
- 是否避免新增孤立角色系统。
- 是否避免让设备商默认承担所有能力差距。
- 是否可以通过现有演示项目验证 Dashboard、需求澄清、能力声明、匹配闭环、交付摘要仍然连贯。

## 8. 推荐实施顺序

1. **先做 P0 快速场景模板**：最直接提升 FAE / 销售客户沟通价值。
2. **再做一页式客户摘要**：让系统能快速输出可分享材料。
3. **同步标准化能力边界**：降低设备商误解和项目责任争议。
4. **随后优化业主业务语言入口**：降低真实客户填写门槛。
5. **最后做 PM / 管理层视图**：在数据结构稳定后再沉淀统计与管理指标。

## 9. 最终结论

这些优化不是要把系统拆成多个角色工具，而是要让不同角色在同一条项目链路上看到自己关心的信息。

系统下一阶段最重要的统一原则是：

> **以同一个项目事实为底座，以不同角色视角组织表达，以统一追溯链和统一交付口径保证可信度。**

只要坚持这个原则，FAE / 销售快速模式、业主低门槛入口、设备能力边界、PM 洞察和管理层价值视图都可以成为同一系统的自然延伸，而不会破坏当前统一设计。
