# IEC 62443 驱动的安全网络规划与选型辅助系统

一个围绕单一项目对象运行的前端原型系统，用于帮助业主、集成商与设备商在统一上下文下完成风险翻译、系统规划、能力声明、差距闭环与交付汇总。

## 一、系统定位

本系统是一个“IEC 62443 驱动的协同分析与交付辅助系统”，不是：
- 标准阅读器
- 自动认证工具
- 自动合规判定系统
- 输入少量问题后直接输出唯一正确架构的生成器

系统希望完成的不是“替代专家判断”，而是把项目前期常见的三次翻译显式化、结构化：
- 业主语言 -> 风险与安全目标语言
- 风险与安全目标语言 -> 系统规划与控制要求语言
- 系统规划与控制要求语言 -> 设备能力与选型语言

## 二、当前系统概况

当前版本已经不是单纯的页面演示，而是围绕一个项目状态对象组织的分阶段工作流，支持：
- 项目元数据统一维护与阶段进度判断
- 业主输入、风险翻译、设计规划、能力声明、匹配闭环的连续状态流转
- Dashboard 工作台、Translation Center 追溯视图、Report Center 交付汇总
- 通过本地规则引擎生成可解释的风险重点、规划建议与匹配结果
- 通过 localStorage / sessionStorage 保留项目上下文并支持演示项目加载

## 三、业务结构

### 1. 三方协同主线

系统围绕三个主要角色组织：
- 业主：描述业务目标、关键资产、暴露面、成熟度和验收偏好
- 集成商：将风险关注翻译为 Zone / Conduit、通信设计、边界控制和能力需求
- 设备商：围绕项目要求提交能力声明、证据类型、边界条件和依赖说明

在此基础上，系统补充两个横向中心：
- 闭环与选型中心：进行要求-能力匹配、差距识别和补偿措施闭环
- 交付与追溯中心：展示从业务输入到能力与差距的完整追溯链

### 2. 当前业务流程

当前实现已经形成如下主流程：

```text
项目建立 / 工作台
  -> 业主输入与风险翻译
  -> 集成设计与要求分配
  -> 设备能力声明
  -> 选型匹配与差距闭环
  -> 追溯查看与交付汇总
```

其中每一阶段都以“可交接结果”为输出，而不是只停留在表单录入。

## 四、页面与路由

- `/` `首页`：系统定位、角色入口、流程概览、进入工作流
- `/dashboard` `项目工作台`：显示阶段进度、缺失输入、推荐下一步、最新交付物
- `/owner` `业主路径`：采集项目背景、业务后果、暴露面、现状成熟度、关键对象与约束
- `/owner/result` `业主交接结果`：输出风险关注、FR 重点、控制目标、集成输入与验收关注点
- `/integrator` `集成设计工作台`：录入设计依据、Zone / Conduit、资产归组、通信流和设计说明
- `/integrator/result` `系统规划结果`：展示通信矩阵、系统规则、能力需求、待确认项和风险保留项
- `/vendor` `设备能力声明`：录入产品信息、能力声明、证据、依赖与适用边界
- `/vendor/result` `设备声明结果`：输出能力摘要、项目适配情况和限制说明
- `/selection` `选型匹配与闭环中心`：展示要求-能力匹配结果、差距项与闭环动作
- `/gap`：兼容路由，当前自动重定向到 `/selection`
- `/translation-center` `翻译中心`：展示业务输入 -> 风险重点 -> 设计要求 -> 能力 / 差距的追溯链
- `/report` `交付中心`：汇总业主交接物、设计结果、声明结果、闭环状态与交付入口
- `/learning` `学习模式`：面向初学者解释 FR、SL、角色边界与常见误区

## 五、系统架构

### 1. 前端技术结构

- `React 19`：页面与状态驱动
- `Vite`：开发与构建
- `React Router`：阶段页面路由
- `Context + hooks`：统一项目状态管理
- `CSS Modules`：页面与组件样式隔离
- 本地静态规则与数据表：支持风险翻译、规划建议与匹配分析

### 2. 项目状态结构

系统以 `src/context/ProjectContext.jsx` 中的单一项目状态对象为中心，统一管理：
- `projectMeta`
- `ownerProfile`
- `riskTranslation`
- `integratorDesign`
- `vendorCatalog`
- `selectionAnalysis`
- `gapClosure`
- `deliverables`

系统会在加载时对历史数据进行归一化，并将状态同步到 `localStorage` 和 `sessionStorage`，从而支持：
- 断点恢复
- 页面之间共享上下文
- 演示项目快速加载
- 旧结构数据的兼容迁移

### 3. 页面层、引擎层、数据层分工

#### 页面层
位于 `src/pages/*`，负责：
- 任务输入
- 阶段结果展示
- 可解释文本组织
- 页面跳转与交互

#### 引擎层
位于 `src/utils/*`，负责将静态规则转成项目结果：
- `riskEngine.js`：把业主输入翻译为风险关注、FR 重点、控制目标、验收关注点
- `planningEngine.js`：把风险结果与设计输入翻译为区域/通道、控制建议、能力需求和规划规则
- `matchEngine.js`：把设备声明与集成要求进行匹配评分和状态分类
- `designInputEngine.js`：整理设计输入与设计依据
- `matchPresentation.js`：匹配结果展示转换
- `reportGenerator.js`：当前提供 JSON 导出能力

#### 数据层
位于 `src/data/*`，提供：
- 能力项定义
- 规则映射
- 行业与枚举
- 交付项定义
- 视图模式定义
- 演示项目数据

## 六、当前功能

### 1. 工作台与阶段推进

`Dashboard` 已经成为当前项目的主控制台，而不是简单导航页。它会根据 `useProjectStatus()` 计算：
- 六阶段完成度
- 每阶段子步骤状态
- 缺失输入提示
- 推荐下一步入口
- 演示项目加载与项目重置

当前阶段定义为：
- 项目建立
- 业主输入
- 集成设计
- 设备声明
- 闭环
- 交付汇总

### 2. 业主输入与风险翻译

业主路径不再只是问卷，而是项目设计输入来源。当前输入重点覆盖：
- 项目名称、业主单位、站点、行业、场景类型
- 人身安全、环境、产能、财务、合规等后果
- 远程运维、第三方访问、暴露面
- 网络隔离、身份管理、日志、补丁等成熟度
- 关键资产、关键系统、外部连接、维护路径、初始边界、连续性要求

风险翻译结果当前输出的核心结构包括：
- `drivers`
- `riskConcerns`
- `frFocus`
- `targetLevelCandidates`
- `controlObjectives`
- `ownerRequirements`
- `acceptanceFocus`
- `explanations`

### 3. 集成设计与要求分配

集成商路径将业主风险输入转为系统规划。当前重点已经覆盖：
- 设计依据说明
- Zone / Conduit 结构
- 资产归组
- 跨区通信流
- 规则建议
- 能力需求矩阵
- 风险保留项

这意味着系统当前已经具备“从风险关注到控制要求，再到能力需求”的连续翻译能力，而不仅是展示静态模板。

### 4. 设备声明与匹配分析

设备商路径当前围绕项目要求组织能力声明，而不是单独维护一个脱离项目的产品库。声明内容逐步覆盖：
- 产品元信息
- 能力声明项
- 满足方式
- 安全等级
- 证据类型
- 依赖与适用边界
- 限制与备注

匹配引擎会把能力项分为：
- `native` 原生满足
- `configured` 配置后满足
- `external` 依赖外部补偿
- `compensating` 通过补偿措施满足
- `missing` 缺失

并进一步计算：
- 分项明细
- 状态分布
- 综合得分
- 推荐等级

### 5. 闭环、追溯与交付

当前系统已经把“差距闭环”并入主流程：
- 在 `Selection` 中查看待闭环能力项和匹配结果
- 在 `Translation Center` 中查看追溯链
- 在 `Report Center` 中查看交付准备状态、闭环项、高严重度和外部依赖数量

`Report Center` 当前汇总以下交付对象：
- 业主交接物
- 集成设计结果
- 设备声明结果
- 闭环状态
- 需求追溯链

## 七、系统特点

相对于更早期的原型思路，现有系统已经体现出以下特点：
- 以项目为中心，而不是以孤立页面为中心
- 以阶段推进为主线，而不是以角色切换为主线
- 以“可交接结果”为输出，而不是只保留输入表单
- 以追溯和闭环为补强，而不是只做一次性推荐
- 以本地可解释规则为底座，而不是黑盒结论

## 九、当前限制

- 当前仍是前端原型，未接入后端、账户体系或真实设备数据库
- 风险翻译、规划建议和匹配分析依赖本地静态规则与模板，不替代正式风险评估
- 输出可用于前期沟通、方案澄清和交付准备，但不等于认证结论
- 报告导出目前以本地 JSON 导出为主，打印与正式文档导出仍可继续增强
